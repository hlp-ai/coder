# v0 最小闭环能力边界

Status: accepted

在锁定技术栈之前，我们先锁定编码智能体 v0 的能力边界，以便后续规划只处理实现选择。选择一次性 CLI 任务、最小工具集和结构化工具调用，是因为“读取→修改→验证”的闭环已经足以用可验证的任务证明智能体可用；更大的工具面、多智能体和长上下文机制会推迟这个验证，而不是加速它。

## 决策

**纳入最小闭环**

- 入口：一次性 CLI 任务 `coder "<任务>"`，跑完退出。
- 动作空间：结构化工具调用（function calling）；不采用 ReAct 文本命令，不采用代码执行动作（shell 命令除外）。
- 工具：读文件、写/局部编辑（搜索替换补丁，带唯一上下文）、列目录/glob、grep、执行命令。
- 上下文：启动前置注入 AGENTS.md；工具失败与测试失败作为观察回填。
- 验证：测试命令取自项目说明或任务，改动后执行并把结果回填；没有命令则跳过验证并明确告知，不自行猜测。
- 控制：必须有迭代上限与预算，具体数值留给实现。
- 安全：工作目录限定；破坏性/不可逆命令拦截；网络一律禁止；写文件与执行命令前交互确认，`--yes` 可跳过但黑名单仍拦截。
- 交付：直接修改工作区文件，输出变更清单与验证结果摘要，不自动提交。
- 可观测：记录每步模型输入输出、工具调用与结果，供复盘与验证。

**明确排除**

MCP、子智能体、repo map、长上下文压缩、提示缓存、Web/IDE 入口、多模态、技术栈（语言/运行时）、模型供应商细节、代码执行动作（shell 除外）、破坏性命令黑名单的具体枚举。这些不占本轮决策的位置，留给后续规划或实现。

**验收样例**

在一个小仓库中修复一个失败的单元测试：改动 1–2 个文件，测试由红转绿。

## 考虑过的选项

- 交互式会话或 issue 链接入口：推迟到闭环验证之后，一次性任务更快达到可判定状态。
- 整文件重写或统一 diff 编辑：搜索替换补丁在 token 开销与格式稳定性之间取得平衡。
- 完整沙箱、网络白名单、多智能体与 MCP：解决的是更后期、更不可信场景的问题，不是 v0 的阻塞项。

## 后果

下一轮规划只需处理技术栈与模型接入；上述排除项若重新引入，需要新的 ADR 取代本决策。
